## Findings

### Blockers

- **B1 [services/changes.py:21 `record`, repositories/changes.py:17, models/change.py:23]** The sync cursor is the global `Identity()` id, assigned when the row is inserted, not when the transaction commits. Writes in one namespace don't lock anything namespace-wide, so they can commit out of id order.
  - **Scenario:** T1 gets id 100 and T2 gets id 101. T2 commits first and a client stores cursor 101. Then T1 commits, and row 100 is never delivered by `list_changes` or the long-poll.
  - **Impact:** a file or folder silently never syncs (FR-SYNC-03). Identity caching on Oracle RAC makes this worse. Found by 3 reviewers.
  - **Fix:** in `change_service.record`, lock the namespace row (`SELECT … FOR UPDATE`) and take a per-namespace sequence (`namespaces.last_change_seq += 1`, stored as `changes.seq` with a unique `(namespace_id, seq)`) as the cursor. This needs a migration. The lock is always taken last, so it adds no deadlock cycle. Add a two-session test where the lower id commits second.
- **B2 [services/uploads.py:219-222]** A replayed `complete` returns the node's *current* state, not the result of this upload.
  - **Scenario:** device A's response is lost and device B then edits the file (rev 6). A retries and gets rev 6 / B's hash, then stores it in its index (transfers.md step 6). A's next scan uploads its own content with base 6, which overwrites B's edit with no conflict. GC then removes B's version.
  - The same path also returns a trashed node as if it were live, and skips `access.require_node`.
  - **Fix:** at completion, store `result_revision` and the version id on `upload_sessions`. On replay, return that exact state (revision, hash, size), still going through `access`. Test: complete, someone else edits, retry, and assert the original revision comes back.

### Should fix

- **S1 [api/v1/uploads.py:43-49]** The chunk PUT keeps the request transaction, and so a pooled connection, open while up to 8 MiB of body streams in. A handful of slow clients (or anyone, on purpose) can exhaust the 5+10 pool, and then every endpoint fails, including long-polls. Fix: end the transaction after `chunk_limit`, the same way `prepare_wait` does, or use short `session_factory()` sessions.
- **S2 [services/uploads.py:209-324, storage/local.py:60]** `complete` has two related problems, and is also ~115 lines long:
  - It locks the parent folder or edited file *before* assembling a blob of up to 10 GB. Every create, upload and ancestor delete in that folder waits minutes.
  - `storage.commit` deletes the staged chunks before the DB commits. Any later failure (name race, DB error, crash) leaves a PENDING session with no chunks, so the retry re-sends the whole file (NFR-REL-04). The name-race path also returns `NAME_CONFLICT` with `details=None`.

  Fix:
  1. Validate the target without locks.
  2. Assemble while keeping the staged chunks.
  3. Lock the target, then re-check the revision, name and quota.
  4. Write the metadata.
  5. Discard the staging directory only after a successful commit (the cleanup job catches anything missed).

  Split `complete` into helpers while doing this.
- **S3 [services/uploads.py:74, 94-99; repositories/uploads.py:30]** Quota for new versions is checked inconsistently:
  - At start, a new version is checked against its size delta, and skipped entirely when `needed <= 0`.
  - `reserved_bytes` then counts the full size of every pending upload against other uploads.
  - Effects: many same-size edits of one file all pass, staging N × 10 GB. A user near quota editing a large file causes other uploads to fail.
  - The `exclude` parameter is unused.
  - Fix: decision D1.
- **S4 [storage/local.py `_write_atomically`, :58]** After `os.replace`, the containing directory, and any newly created `blobs/ab/cd` directories, aren't fsynced. A power loss after the DB commit can leave a visible version with no blob (NFR-REL-03). Fix: fsync the directory after `replace` and after `mkdir`, on POSIX only.
- **S5 [services/uploads.py:148, 363]** Nothing ever removes staged chunks of expired or abandoned uploads, and no `jobs/` package exists. Expired reservations stop counting against quota, but their bytes stay on disk, so a user can fill the server disk beyond quota by starting uploads and letting them expire. A chunk PUT racing `cancel`/`complete` can also recreate `staging/<id>/`. Fix: decision D2.
- **S6 [core/error_handlers.py:55-64]** Access-denied events from hidden 404s record only method, path and code. When the probed ID is in the body (`POST /nodes`, `/uploads`, `/changes/wait`), the event doesn't say which item was targeted (FR-AUDIT-02). Fix: optional `AuditTarget` on `AppError`, set by `access.require_node`, `require_namespace` and `_require_upload`, and passed to `record_now`.
- **S7 [services/uploads.py:86, 167-174, 231; services/nodes.py:79, 108, 158, 201, 243]** Error `details` are inconsistent for a client that must parse them:
  - `VALIDATION_ERROR` details come in three shapes: a list of `ValidationIssue`, a dict `{expected_bytes}`, or `None`.
  - `UPLOAD_INCOMPLETE`, `FILE_TOO_LARGE` and `RANGE_NOT_SATISFIABLE` details have no typed models.
  - `NameConflictDetails` and `RevisionConflictDetails` live outside `error_details.py`.

  Fix:
  - Always send `[ValidationIssue]` with a stable `type` (`chunk_size`, `not_a_folder`, `root_not_deletable`, …).
  - Add `UploadIncompleteDetails`, `FileTooLargeDetails` and `RangeNotSatisfiableDetails`, and keep all detail models in `error_details.py`.
  - Add the two new codes to the conventions status table.
- **S8 [shared/schemas/sync.py:34; nodes.py:34-36, 44; uploads.py:50]** Response enums (`ChangeOut.type`, `NodeOut.kind`, `NamespaceOut.kind/role`, `UploadOut.status`) are strict. Adding a value later (for example a `restored` change for FR-TRASH-02) makes installed clients fail to parse whole change pages, so sync stops (FR-UPD-04). Fix: decision D3.
- **S9 [services/nodes.py:156, services/access.py:54]** A retried `DELETE` after a timeout returns 404, the same as for an item that never existed. The client has no way to confirm that its own delete succeeded, because `GET` also hides trashed items and `/trash` comes in F3. Fix: return 204 when the node is already in the trash from a delete of this same item, the caller can write to it, and `revision == if_revision + 1`.
- **S10 [api/v1/nodes.py:100-101]** A `Range` header with a value of more than 4300 digits makes `int()` raise `ValueError` (Python's int-string limit), giving a logged 500 instead of being ignored. Fix: limit the digits in the regex (`\d{0,19}`).

### Nits

- **N1 [services/access.py:54]** The trashed check comes before the role check, so probing another user's *trashed* node isn't audited as denied. A `lock=True` call also locks another user's row before checking ownership. Resolve the role first.
- **N2 [services/access.py:35-40, services/nodes.py:93]** `require_namespace` loads the namespace twice, and `list_namespaces` calls it again for namespaces it just loaded. Set `role=OWNER` directly.
- **N3 [services/uploads.py:263-267]** A quota failure at completion writes no `file.uploaded` failure audit event, unlike the hash-mismatch path.
- **N4 [services/uploads.py:367]** Cancelling a completed upload returns 400. 409 fits better, because the upload is in the wrong state rather than the request being malformed.
- **N5 [services/uploads.py:165]** For an empty upload, the chunk-index message reads "between 0 and -1".
- **N6 [api/v1/nodes.py:60-91]** `If-Range` is ignored, so resuming across a new version splices two versions together. The client's hash check catches it, but the whole download is wasted.
- **N7 [services/nodes.py:233]** On an empty file, `Range: bytes=0-` gives 416. A client that always sends `bytes=<.part size>-` would fail on zero-byte files.
- **N8 [shared/schemas/sync.py:62]** `WaitIn.cursors` values have no `ge=0`.
- **N9 [services/changes.py:82]** The long-poll's 404 doesn't say which namespace failed. That will matter once mounts can be removed (F4).
- **N10** Small contract items:
  - Reserve a `CURSOR_INVALID` code (meaning "do a full resync") now, for cursors after a DB restore or journal compaction.
  - Use `AwareDatetime` in response models.
  - Document that `complete` returns 200, not 201.
- **N11 [api/v1/changes.py]** Nothing limits how many long-polls one user runs at once. Each one occupies a threadpool slot shared with all sync routes.
- **N12 [models/change.py:25, file_version.py:17]** The foreign keys to `nodes` mean the trash purge (FR-TRASH-03) must decide what happens to journal rows. Note it for the F3 design.

## Decisions needed

- **D1 (S3) Quota reservations:**
  - (a) Reserve and check the full `size_bytes` at start for every upload (simple, and bounds staging disk). Editing a large file then needs that much free space temporarily.
  - (b) Store a per-session `reserved_bytes = max(delta, 0)` and sum that. Fairer, but staged bytes of same-size edits aren't bounded until S5's cleanup exists.
- **D2 (S5) Staging cleanup:**
  - (a) Build the `expire-uploads` job now: `dropshare-server jobs run expire-uploads`, which also sweeps staging directories of sessions that aren't pending.
  - (b) Defer it to F3 as planned, and record the gap.
- **D3 (S8) Forward-compatible enums:**
  - (a) Make response enums `Enum | str` (left_to_right), as `ErrorBody.code` already is, with the client rule "unknown change type → refetch the namespace".
  - (b) Keep them strict for now and add a `restored` change type in F3.

## Lessons for CLAUDE.md

- One-line rule proposal for `api-endpoint` → `references/database.md` §2: "A sync cursor must follow commit order: never use a global identity id as a cursor; take a per-namespace sequence under a namespace row lock." The current rule ("the ID doubles as the sync cursor") is what led to B1.
- Testing rule proposal: "Any write path that clients retry or poll needs a test with two interleaved transactions."
