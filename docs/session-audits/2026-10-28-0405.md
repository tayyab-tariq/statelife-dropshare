## Findings

### Blockers

- **B1 [client/src/dropshare_client/sync/core.py:371-402 with sync/engine.py:337-341] A failed move splits into two cycles and the old path is then deleted.** `_execute` puts only `action.key` (the move's target) in `result.retry` with a backoff. Because every move sets `again`, the engine then does `setdefault(now)` for every dirty root, so the old path runs right away on its own. In that cycle the node isn't in scope at its new path, so the ordinary rules plan DELETE_LOCAL (server move, e.g. Word holds the file on Windows) or DELETE_REMOTE (local move, e.g. 503 on the PATCH). Nothing is lost (Recycle Bin / server trash), but a rename becomes delete + re-transfer with new node IDs, which FR-SYNC-10 forbids, and no FR-SYNC-08 prompt below the thresholds. `Device.sync` re-adds every path, so tests miss it. **Fix:** on any failure of a MOVE_* action, give the same retry delay to the target, the old key and the current local key. As a second guard, a cycle that covers only some paths widens itself to a remote node's current path (`tree.path_of`) instead of deleting a base entry whose node is alive elsewhere. Add an engine-level test with the real retry scheduling.
- **B2 [server/src/dropshare_server/services/nodes.py:189-205, repositories/nodes.py `ancestor_ids`] Two concurrent folder moves can create a cycle.** Only the target folder and the moved node are locked; the ancestor walk isn't. Moving A into B/b1 while B goes into A/a1 lock disjoint rows, both checks pass, both commit: A and B form a cycle cut off from the root. Clients then see both trees as deleted and recycle the local copies; later moves of those nodes raise `RuntimeError` (500). Opposite moves can also deadlock (ORA-00060 → 500). Found by the security, code and sync reviewers. **Fix:** when the parent changes, lock the namespace's root node first (every other write locks the root only as a parent, and the namespace row stays last), then check. Add a two-session test.

### Should fix

- **S1 [client/src/dropshare_client/sync/reconciler.py `_find_moves`]** A move that is recognised but postponed (overlapping another move, or a deferred target still being written) is skipped with `continue`, so the ordinary rules delete its old path. Example: rename `A`→`B` and drag `x.txt` into `B` in one debounce. **Fix:** add the old key to `waiting`.
- **S2 [reconciler.py `_local_location`, core.py `_identify_new`]** The file still at the old path never has its file ID looked up, so a new item elsewhere with the base's file ID always wins. Emacs/vim backups (`report.txt~`, not ignored) then take the node and its identity; on another device that edited the file, OQ-27 moves the edit to the backup name with no conflict copy. Hard links behave the same. **Fix:** if an item of the same kind is still at the old key, treat it as an edit in place and don't pair elsewhere.
- **S3 [reconciler.py `_files_at`]** The mass-delete count includes files a move in the same plan takes out of a deleted folder (move 600 files out of `Old/`, delete `Old/` → asked to confirm 600 deletes). **Fix:** subtract moved-out base keys.
- **S4 [reconciler.py `_find_moves`, `reconcile`]** O(base × moves): `areas` is a list rebuilt per base key and every key is checked with `is_within` against it. Moving 5,000 separate files in a 100k-item tree is ~10⁹ checks (NFR-PERF-03). **Fix:** sets plus an ancestor walk (O(depth) per key).
- **S5 [server/src/dropshare_server/core/config.py `min_client_version`] Decision needed (D1).** Clients from before this change don't know `MOVED`: they re-fetch the node (no crash), but apply another device's rename as Recycle Bin + re-download, so a large folder rename triggers their mass-delete prompt. **Options:** (a) record it as an interim in OQ-15 and the release notes; (b) raise `MIN_CLIENT_VERSION` to the release that ships MOVED support once it's rolled out. Also proposed: a release-order rule "server before clients" (a new client against an old server gets 405 on PATCH and lists the item as can't sync).
- **S6 [client/tests/sync_fakes.py `FakeFileServer.move`]** The fake answers differently from the real server: 404 instead of 400 `not_a_folder` / `root_not_movable`, no `validate_name()`, and no `details` on `into_itself`. No test covers a local rename to a name the server refuses. **Fix:** match the server, and add that matrix test.

### Nits

- **N1** `services/nodes.py:175` validates the name before the access check, so a bad name on someone else's node gives 400 without an audited denial. Validate after the first `require_node`.
- **N2** `reconciler.py _local_location`: matching by content accepts empty files. Skip `size == 0`.
- **N3** `platform/__init__.py`: on Windows a folder appearing at a file's target gives PermissionError, not FileExistsError, so it's backed off as a lock. Treat PermissionError with an existing target as LocalChangedError.
- **N4** `executor.py _move_local` finishes the journal row before `move_entries`; `_move_remote` after. Use one order (after).
- **N5** `executor.py _move_remote`: if both `parent_id` and `name` end up None, `NodeUpdateIn` raises a pydantic error in the executor. Guard and only record the entry.
- **N6** `test_windows_fs.py` sets `device.core._scanner._file_identity`. Pass the identity through `Device.restart`.
- **N7** `reconciler._find_moves` is ~65 lines with four jobs; split the two direction branches into helpers (with S4).
- **N8** `repositories/nodes.py ancestor_ids` runs one query per level with no depth cap; fine for now, could be a recursive CTE.
- **N9** A renamed folder's children look new, so every file is hashed before the one PATCH. Not a regression.
