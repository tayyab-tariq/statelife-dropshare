## Findings

### Blockers

- **B1. [server/src/dropshare_server/repositories/changes.py:27]** Purged items' journal rows are never served.
  - `list_after` still inner-joins `changes` to `nodes`. Once an item is purged, its rows (including its `trashed` row) vanish from `GET /namespaces/{id}/changes`. That defeats migration `c4a7d2e9f310` and OQ-38.
  - A device offline longer than the trash retention, or one that falls behind while someone deletes and then empties the trash, never learns the item was deleted. It keeps the files, and its index points at node IDs that no longer exist.
  - If the newest rows in a namespace all belong to purged nodes, the feed returns an empty page and the cursor doesn't move. Meanwhile `latest_cursors` (no join) still reports a newer cursor, so the client's wait → changes loop repeats indefinitely. Released 0.2.0 clients are affected too.
  - Found by all three server-side reviewers. Confirmed in the code.
  - The existing test only checks that the row stays in the table, not that the feed returns it.
  - **Fix:** store `mount_namespace_id` on the `Change` row (new migration plus backfill) and drop the join. A quicker alternative is `outerjoin`, but a purged mount's earlier rows then lose their mount flag. Add an API test: delete, purge, then read `/changes` from the old cursor; the `trashed` row comes back and the cursor advances.

- **B2. [server/tests/conftest.py:51, server/tests/test_auth_api.py:344, server/tests/test_cli.py]** Server tests read the developer's `server/.env`. The suite fails today.
  - `_settings` claims explicit values, but `Settings.model_validate` still reads `ENV_FILE`. The `cli` fixture's `Settings()` does too.
  - `MIN_CLIENT_VERSION` from the local `.env` leaks in. The test hard-codes 0.1.0, which has been wrong since M8 changed the default to 0.2.0. It only passed while the local `.env` said 0.1.0.
  - The same leak reaches the new settings: `AUDIT_RETENTION_DAYS` (the CLI test expects "365 days"), and `AUDIT_PURGE_DB_*`, which would point the purge-audit test at another account.
  - This was introduced in M2 and first fails now.
  - **Fix:**
    - Build test settings with `_env_file=None`.
    - In the `cli` fixture, set the job and version variables explicitly, or point `ENV_FILE` at an empty file.
    - Make the test assert the value from the settings it uses, not a literal.

### Should fix

- **S1. [server/src/dropshare_server/services/trash.py:243, 264]** Restore never re-checks `trashed_at` after locking the target folder (`access.require_node` does).
  - If the folder or one of its parents is trashed between the unlocked read and the lock, the restored item comes back live inside the trash. Clients get a CREATED row under a folder they dropped.
  - When that folder is later purged, `children_outside` quietly re-parents the live item with a stale `live_key` and no journal row, so the item can no longer be seen by sync.
  - **Fix:**
    - Re-check after every `get_for_update`, and return 409 so the client can retry.
    - Also re-run `_require_shared_folder_live` after locking.
    - In `_purge`, refuse rather than re-parent when `children_outside` returns a live node.

- **S2. [server/src/dropshare_server/services/trash.py:186–195]** `_free_name` runs only for the restored item itself.
  - For the owner's deleted shared folder, the contents hang under the shared folder's root, which never goes to the trash. The owner can still write there, for example from a device that hasn't synced the delete yet.
  - If a name is taken that way, every restore attempt returns 409 "just created here" and can never succeed.
  - **Fix:** free names for every restored node whose parent is outside the restored set.

- **S3. [server/src/dropshare_server/services/trash.py:434–448 vs services/uploads.py:245, 310]** Lock-order deadlock between purge and upload `complete`.
  - `complete` holds the upload row while it assembles the blob, then locks the target folder.
  - `_purge` locks the trash group and the owner row, then deletes the upload rows.
  - Each waits for the other. One request fails with a 500 (ORA-00060 on Oracle). No data is lost.
  - **Fix:** in `_purge`, lock the group's pending uploads with `NOWAIT` and answer 409 "try again" if one is busy. The job skips such items.
  - Verdict: plausible. The lock sequence was confirmed by reading the code; not reproduced.

- **S4. [server/src/dropshare_server/services/trash.py:382–404]** `DELETE /trash` empties everything in one request transaction.
  - It holds node locks and the owner's quota row (blocking that user's uploads) and risks proxy timeouts.
  - `delete_nodes` scans the session's identity map once per item, so the work grows quadratically with the trash size.
  - The plan accepted this tradeoff, but three reviewers flagged it.
  - **Fix:** commit per batch, as `purge_expired` does, or cap the items per call and report what remains.

- **S5. [server/src/dropshare_server/repositories/nodes.py `owned_trash_roots`, services/trash.py:388]** `EmptyTrashOut.removed` and the `trash.emptied` audit count include hidden mounts the user never saw in the list.
  - **Fix:** count only items the user can see, and purge hidden mounts without counting them.

- **S6. [server/src/dropshare_server/services/blobs.py:50–57]** The orphan sweep has no guard against a mass delete.
  - Running `gc-blobs` against the wrong or empty schema, or right after restoring the database from an older backup (NFR-REL-06), deletes every stored file. This is irreversible.
  - **Fix:** abort when there are no version rows but storage holds blobs, or when orphans exceed a threshold, unless `--force` is given.

- **S7. [server/src/dropshare_server/storage/local.py:87–90]** `blobs()` calls `stat()` on paths that the gc run itself, or a concurrent API purge, may delete. A `FileNotFoundError` then aborts the whole run.
  - **Fix:** skip paths that have gone.

- **S8. [client/src/dropshare_client/services/trash.py:40–46]** `delete_forever` treats every 404 as success.
  - The server also answers 404 when the item was restored meanwhile. The user is then told "Deleted for good" while the item is back in their files.
  - **Fix:** have the server answer a live (restored) node with 409, or 404 with a `restored` detail, and have the client report `NOT_IN_TRASH`. Treat 404 as done only on the client's own retry.

- **S9. [server/src/dropshare_server/services/trash.py:86–87]** Role-based refusals in `_visible` aren't audited as denials.
  - This covers a viewer, or an editor acting on someone else's delete. FR-AUDIT-01 requires authorization failures to be audited.
  - **Fix:** `not_found(denied=True, target=…)` when the caller has a role but may not act on the item. This leaks nothing, because they already have a role on the namespace.

- **S10. [server/src/dropshare_server/services/trash.py:372]** The owner-only 403 has no `target`, so the denial event lacks the target type and ID (FR-AUDIT-02).
  - **Fix:** pass `target=("node", id)`.

- **S11. [server/src/dropshare_server/services/audit.py `purge_expired`]** Batches commit one by one, and `audit.purged` is written only after the loop. A failure partway (DB error, killed job, bad app credentials) leaves deleted audit rows with no record (FR-AUDIT-03).
  - **Fix:** record in a `try/finally` with the count removed so far and the outcome, or record per batch.

- **S12. [client/tests/client_fakes.py `_trash_act`; client/tests/cloud_fakes.py `restore`]** The test fakes behave differently from the server.
  - The client fake gives a restored item a new ID at the top level, and a repeated restore gets 404. The server keeps the ID and parent, and answers 200.
  - The cloud fake restores items that were deleted earlier on their own, applies no "(restored)" suffix and recreates no parent. It also bumps no revisions for the shared folder's contents.
  - **Fix:** mirror the server, then add sync tests for a restore whose name is taken and a restore with a recreated parent.

- **S13. [client/src/dropshare_client/controllers/trash_controller.py:69–86]** Overlapping reloads (opening the page, F5, the reload after an action) aren't ordered. An older list can land last and show restored items in the trash again.
  - **Fix:** a sequence number per refresh; drop stale results.

- **S14. [client/src/dropshare_client/ui/app_shell.py:270, 222]** The trash isn't cleared when the session expires (`_needs_sign_in`) or reset on `_signed_in`, and `clear()` leaves the error and status messages behind. If someone else signs in on a shared PC, they can briefly see the previous user's trash.
  - Shared with me has the same gap (from M8).
  - **Fix:**
    - Clear on `_needs_sign_in` and on `_signed_in`.
    - Clear the messages and the selection when the view is cleared.

- **S15. [client/src/dropshare_client/controllers/trash_controller.py:83, ui/trash_view.py:113]** Any failed reload, including the quiet reload after an action, replaces a filled table with the error page (ui.md §3).
  - **Fix:** with rows shown, report the failure in `trashError` and keep the table, as Shared with me does with `quiet`.

- **S16. [client/src/dropshare_client/controllers/trash_controller.py `_each`, `empty`]** Restoring or deleting many items, or emptying the trash, shows no progress and can't be cancelled (ui.md §6). The loop also keeps sending requests after the user quits.
  - **Fix:** a "Restoring n of m…" signal, plus a stop event checked between items and set on quit.

- **S17. [client/src/dropshare_client/ui/trash_model.py, ui/trash_view.py]** Table polish that the browser view already has:
  - no file or folder icons;
  - no tooltips;
  - no middle-elide, so long names lose their extension.
  - **Fix:** copy what the browser view does.

- **S18. [client/src/dropshare_client/ui/trash_view.py:153, 180; controllers/messages.py `confirm_delete_forever`]** Keyboard and screen-reader users get no feedback in two places:
  - The reason "Delete for good" is disabled exists only as a tooltip on a disabled button, so they never hear it. Pressing Delete does nothing and says nothing.
  - With a mixed selection, items they can't delete are dropped silently, and the confirmation names none of them.
  - **Fix:** say the reason in the status line. Name up to 3 items plus "and N more" in the confirmation, and say how many stay in the trash.
