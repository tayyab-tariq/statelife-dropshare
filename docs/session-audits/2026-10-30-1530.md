## Findings

### Blockers

- **B1. [client/src/dropshare_client/sync/core.py:727, 748–750] A pause, stop or going offline doesn't reach queued transfers.**
  - Every prepared transfer is put into the pool at once, and none still waiting is cancelled.
  - After `stop.set()`, each queued upload still runs its resume `GET` or `POST /uploads`, reserving quota for 24 hours. `stop` is first checked inside `_send_chunks`, so a 0-byte file completes anyway.
  - Each queued download still sends its GET.
  - Offline, each waits out the 10 s connect timeout, 4 at a time. 2,000 queued files block the engine for about 80 minutes, and quitting hangs.
  - This breaks FR-SYNC-05 ("resume continues where it stopped" and pause within a moment). Found by both the code and sync reviewers; confirmed.
  - **Fix:**
    - Submit at most `max_transfers` at a time and prepare each only when a slot frees up. That also fixes S1.
    - Cancel futures that haven't started.
    - Check `stop` at the start of `work` and before `_start`/`_complete`.
    - Test with more files than workers, and with a 0-byte file.

- **B2. [client/src/dropshare_client/services/files.py:229–237, 293–306; sync/core.py:435] A completed upload session can be replayed onto a file that has moved since.**
  - When the answer to `complete` is lost, the session row is kept, and recovery settles the upload from the journal without forgetting the row.
  - Later, identical content saved at the old path has the same key. `GET` returns COMPLETED, and the server's `_replay` returns the node where it is now.
  - `finish` then binds the new local file to that node:
    - two index entries point at one node;
    - the new file never reaches the server;
    - sync loops on the rename.
  - Persisting sessions widened this from one app run to 2 days and across restarts. Contract reviewer: blocker; sync reviewer: should fix. Confirmed in the code.
  - **Fix:** do all three.
    1. Forget the session wherever an upload is settled other than by `upload()`: recovery, record or link.
    2. On a replayed COMPLETED, check the node still matches the target: the parent and name for a new file (allowing a mount's root), the node ID for a version. On a mismatch, forget the row and start a new upload.
    3. Add a test.

### Should fix

- **S1. [sync/executor.py:262, 318]** `prepare` calls `transfers.started` and begins the upload journal for every file before any moves. Transfers then shows the whole batch as active, and each journal row costs an fsync. This is fixed together with B1.
- **S2. [sync/core.py:715, 730]** The "items to do" count includes actions already done before the batch, and is re-sent every 0.2 s even when unchanged.
- **S3. [sync/core.py:753]** `contextlib.suppress(Exception)` around settling in the fatal handler is the swallow pattern CLAUDE.md §5 forbids: a failed `finish` leaves no log line. Log it. Also, transfers settled there skip `_done` (nit).
- **S4. [sync/core.py:702] (FR-XFER-03, NFR-PERF-02)** The engine stays in `_transfer_all` until the whole batch ends.
  - A small file saved during a multi-GB transfer isn't planned until that transfer finishes, so the 10 s target is missed and 3 slots sit idle.
  - **Fix:** let later cycles feed the running pool (preferred), or state the limit in OQ-39.
- **S5. [server services/uploads.py:141–143 with client sync/core.py `_api_failed`]** Parallel uploads of new versions each reserve their full size (D1).
  - Near the quota, the third and fourth fail with QUOTA_EXCEEDED, although they would fit one after another.
  - They are parked in "Can't sync" until the file changes, and the user is wrongly told they're out of space.
  - **Fix:** while other transfers in the batch are in flight, retry QUOTA_EXCEEDED with backoff; park it only when nothing else is running.
- **S6. [services/files.py:123, store/index.py:488–497]** The session key includes the hash and size. An interrupted upload whose file is then edited leaves the old server session reserving quota for 24 hours, and the client never cancels it.
  - **Fix:** key by target only, keep the hash and size in the row, and `DELETE` the old session when the content differs.
- **S7. [client/tests/sync/test_matrix_crashes.py:62–68, 96–98]** The crash sweep's invariant only checks that content exists somewhere.
  - It wouldn't catch a crash leaving an edit only in a trash or bin ("edit wins", FR-CONF-02).
  - **Fix:** also assert that every piece of content live in the reference run is live after the crash.
  - Also note that crash-point numbering can differ when several transfers run. Run these cases with `max_transfers=1`, or say so in the docstring.
- **S8. [server/tests/test_uploads_api.py:545]** The deadlock test uses `time.sleep(0.3)`.
  - On PostgreSQL it can pass without exercising the scenario.
  - On Oracle, where foreign-key checks don't lock the parent row, `NOWAIT` can fail spuriously.
  - **Fix:** poll `pg_locks` until the starter waits, and skip unless the database is PostgreSQL. The scenario only exists there.
- **S9. [sync/executor.py:117–125]** The UPLOAD/DOWNLOAD branch in `Executor.run` is never reached. Remove it, or raise as `prepare` does.
- **S10. [.claude/skills/sync-engine/references/transfers.md:10–11, 27; algorithm.md:37 and the §2 table]** These contradict the code:
  - "2–3 chunks of the same file in flight";
  - "upload ID stored in the journal";
  - "two queues by size";
  - "the index has one writer";
  - the `upload_sessions` table is missing.
  - The skill references and docstrings (`transfers.py:4`, the `Transfer` docstring) need updating.
- **S11. [client/tests/sync/test_parallel_transfers.py:89, 98, 109, 117]**
  - `most_on_wire == 4` / `== 2` relies on threads overlapping within 20 ms.
  - The stop is fired by a timer.
  - The "overtake" test passes with a sequential engine.
  - **Fix:** use a barrier until `max_transfers` are on the wire; stop from inside the fake; prove small files finish while the big one is still on the wire. Pass `max_transfers` through `Device.restart`, not a private attribute.
- **S12. [scripts/perf/perf_common.py:28, 71–101; initial_sync.py:101, 148; metadata_load.py:33]** The perf scripts:
  - make accounts in whatever database `server/.env` points at, whatever `--server` says;
  - use a password that is in the repo;
  - never clean up;
  - treat any `AppError` as "the user already exists".
  - Also: `initial_sync` uses `SIGKILL` (missing on Windows, where the full-scale run is planned) and signs in again on every 2 s poll. `metadata_load` setup failures silently drop users, and the run can still report "met".
  - **Fix:**
    - refuse unless the server and database are local, or `--allow-remote` is given;
    - a random password per run;
    - a `--cleanup` that disables the `perf-*` accounts through the service;
    - catch only the name-conflict error;
    - `process.kill()`;
    - sign in once;
    - count setup failures.
  - Security and code reviewers.
- **S13. [services/files.py:135 with app.py:175, services/sharing.py:136]** The in-memory session store is shared across sign-ins, and its key has no user in it.
  - User B uploading a shared file that user A tried in the same run gets a 404, and the server records an `access.denied` against B.
  - This existed before (`_uploads`), but this session touched it.
  - **Fix:** put the user in the key, or clear the store on sign-out.
