## Findings

### Blockers

- **[client/src/dropshare_client/app.py:115-121]** `_install_pending` catches only `UpdateVerificationError`. `forget()` (unlink), `stat()` and `file_sha256()` inside `verify` can raise `PermissionError` or another `OSError`, for example while antivirus scans the new installer. That escapes `main()` before any window opens, so DropShare crashes at startup with nothing shown. **Fix:** catch `OSError` around `forget` and `verify`, log it, return False. Add a test where the hash raises `PermissionError`. *(code-reviewer, confirmed)*
- **[client/src/dropshare_client/controllers/update_controller.py:148-150]** `stop()` (sign-out) only stops the timer. State, release, the downloaded update, `_urgent` and `_on_restart` all carry over to the next account. A stable user signing in after a beta user is offered and can install the beta build, which contradicts OQ-49. `_urgent` also makes the dialog pop up by itself for them. **Fix:** reset everything to IDLE in `stop()`. Files can stay, since `download()` checks a reused installer again. Add a sign-out/sign-in test. *(code-reviewer, confirmed)*

### Should fix

- **S1 [client/src/dropshare_client/services/updater.py:95-139]** Nothing ties the installer bytes to `release.version`. A compromised server, or a local same-user edit of `pending.json`, can label an older, validly signed installer as `9.9.9`, and the client runs it silently: a downgrade. **Fix:** after the signature check, read the installer's version resource (Inno sets `VersionInfoVersion`) and require it to equal `release.version` and be above the running version. *(security)*
- **S2 [shared/src/dropshare_shared/signing.py:36-42, _authenticode_windows.py:94-109]** The publisher is matched only on the certificate's display name (CN). Another publicly trusted certificate with the same CN passes both the client and the CLI check. **Decision needed:** also pin the certificate thumbprint(s) or the full subject (O, C, issuer) in `build_info.json` and `RELEASE_PUBLISHER`, as an allow-list that supports renewal. *(security)*
- **S3 [installer/dropshare.iss, client/src/dropshare_client/app.py:186-201]** There's no `SetupMutex`. During a "Restart and update", the user can start DropShare again. It finds `pending.json` and starts a second installer, and the two race over `{app}\_internal`, leaving a broken install. **Fix:** add `SetupMutex=StateLife DropShare setup`, and have the app skip the pending install (or wait) while that mutex exists. *(sync + code, merged)*
- **S4 [installer/dropshare.iss:84-99]** If DropShare takes longer than the 2-minute silent wait to exit, Setup aborts and nothing restarts the app, so sync stays stopped until a manual start. **Fix:** on a silent timeout, `Exec` the existing `{app}\DropShare.exe` before aborting, or wait without a limit when the update came from the app. *(sync)*
- **S5 [client/src/dropshare_client/services/config.py `_to_json`, sync/binding.py:52-62]** Because the built-in URL isn't saved, a later build with a different built-in URL (or the same server written differently) changes `server_url`. The sync binding then no longer matches and raises `ForeignFolderError`, which breaks "sync state survives the update". Nothing is deleted. **Decision needed:** save the address once an account is signed in (my recommendation), or identify the server by something it returns rather than by the URL string. *(sync + code, merged; this undoes part of step 6's fix)*
- **S6 [client/src/dropshare_client/services/updater.py:155, controllers/update_controller.py:171-192]** A release withdrawn after a client downloaded it, or chose "next restart", is still installed, despite the runbook saying clients stop being offered it. **Fix:** check `latest` again before acting on READY or pending; drop the update if the release ID changed, and install as before only when offline. *(contract)*
- **S7 [controllers/update_controller.py:196-198, ui/app_shell.py:396-400]** The forced-update (426) path:
  - **Dead end:** if nothing newer is published, the client says "syncing has stopped" and "DropShare is up to date" at the same time. FROM_SOURCE or FAILED give the same dead end.
  - **No progress:** download progress shows only in Settings.

  **Fix:** an urgent check that doesn't end READY shows a message in the main window, such as "No update is available yet; contact your administrator". While urgent, mirror the status there too. *(contract + UI, merged)*
- **S8 [controllers/update_controller.py:187-192, 234-254]** If "Update on next restart" fails (an `OSError` writing `pending.json`), the state goes to FAILED and the ready update disappears from the UI. The action can also be started twice. **Fix:** go back to READY whenever `_update` is set and the error isn't a verification failure, and block re-entry while remembering. *(code)*
- **S9 [server/src/dropshare_server/services/releases.py:256-265]** `MinimumVersion.current` holds its lock while it queries the database. With a slow database or an exhausted pool, every API request waits behind that read. **Fix:** under the lock, decide whether a refresh is due and mark it in progress; read without the lock; store the result under the lock. *(code)*
- **S10 [scripts/build_client.ps1:20,63]** `-TimestampUrl` is optional for signed builds. An untimestamped signature stops verifying when the certificate expires, which strands clients that are forced to update. **Fix:** require it unless `-Unsigned`, as packaging.md already says. *(security)*
- **S11 [ui/update_dialog.py:59-65, update_controller.py:132]** The dialog closes before the final check runs, and INSTALLING shows "ready to install". Failures appear only on the Settings error line, which can't be seen from the 426 page. **Fix:** keep the dialog open, with its buttons disabled and a "Checking the update before installing…" line, until install or remember finishes; show errors inline; give INSTALLING its own status text. *(UI)*
- **S12 [ui/settings_view.py:208-222, controllers/messages.py `UPDATE_CHECK_FAILED`]**
  - **Not announced:** a check the user started doesn't announce its result to Narrator.
  - **Focus lost:** focus is lost when "Check for updates" is disabled.
  - **Failure copy:** the failure line says neither why nor what to do (NFR-UX-03), and the reason disappears after leaving Settings.

  **Fix:** `announce()` the result of a check the user started; move focus to "Install update…" when it appears; show the reason, or "Choose Check for updates to try again", in the Updates line. *(UI)*
- **S13 [app.py:108-121, _authenticode_windows.py:117]** The install at the next start runs before any UI exists. That's acceptable as blocking, but it can take 10–60 s when the revocation check is slow, with nothing visible, and a second launch during it is swallowed. Also, offline, the revocation check fails and `verify()` *deletes a good installer*. **Fix:** show a tray message or a small label during the check. For a revocation failure while offline, keep the file and don't install now (tell a revocation failure apart from a bad signature) rather than discarding it. *(UI + security, merged)*
- **S14 [docs/deploy/client-release.md:56, requirements §15]** Installed 0.2.0 clients have no updater. If the first stable release raises `--min-supported` above 0.2.0, they're stranded behind a 426 and need a manual reinstall. **Fix:** keep `--min-supported 0.2.0` until the first updater-capable release has been installed everywhere by hand; say so in the runbook and in a requirements §15 note. *(contract)*
- **S15 [.claude/settings.json:35,38]** Your edit uses `//` comments, which makes the file invalid JSON (`json.load` fails at 35:7), and it opens every `.env.*` file (for example `.env.production`) to reading. **Suggested:** restore both deny rules and add `"allow": ["Read(./server/.env.example)", "Edit(./server/.env.example)"]`. I haven't touched it: it's your settings file, and it's not part of the suggested commits. *(security)*

## What changed (summary)

- **Server:** a `client_releases` table (installers kept in `StorageBackend.write_blob`, kept by gc-blobs) and `users.update_channel`, in one migration. A CLI for `releases publish|list|withdraw` and `users set-channel`; publishing refuses an installer whose Authenticode signature doesn't verify or names another publisher.
- **API:** `GET /client/releases/latest` and `/{id}/installer` (ranged). The version check is split so refresh and update endpoints accept any version. The minimum version is now the higher of the setting and the latest stable release's minimum (cached for 60 s).
- **Shared:** release schemas, `RELEASE_NOT_FOUND`, and `signing.py` (a ctypes `WinVerifyTrust` check used by both the CLI and the client).
- **Client:** `build_info.json` (built-in URL and publisher); an `Updater` service (resumable download, checksum and signature, pending-install file); an `UpdateController` with Settings › About, an update dialog, the notification, install now or on next restart. The download loop is shared with file sync.
- **Packaging:** PyInstaller spec, Inno Setup script (per-user, link scheme, waits on a running mutex, uninstall clean-up), `build_client.ps1`, an icon renderer, and the release runbook.
