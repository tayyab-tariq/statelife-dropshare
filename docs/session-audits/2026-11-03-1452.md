## Findings

### Blockers

- **[docker-compose.yml:52-58]** `idle_in_transaction_session_timeout=60s` breaks completing large uploads. `complete_upload` holds its transaction, with the upload row locked, while `storage.commit` copies and hashes the whole file, up to 10 GiB, over Docker Desktop's slow Windows bind mount (`services/uploads.py:249-271`). PostgreSQL ends the connection after 60 s, the client gets a 500, an orphaned blob is left behind, and every retry fails the same way, so the file can never be uploaded. The compose comment claiming it is safe is wrong; I missed `complete` when checking. **Fix:** remove the setting and its comment (keep `log_lock_waits`).
- **[.github/workflows/deploy.yml:5-8, docs/deploy/windows-docker.md §3-4]** The self-hosted runner has Docker access on the production host, which amounts to admin, and nothing limits what runs on it. Any branch's workflow can target the label `dropshare`. `workflow_dispatch` on another branch runs that branch's copy of the workflow with the production secrets unless the environment is limited to `main`. If the repo is public, fork PRs can reach the runner. **Fix (settings plus runbook):**
  - Keep the repo private.
  - Limit the `dropshare-production` environment's deployment branches to `main`.
  - Protect `main` (PR plus review).
  - Require approval for outside contributors' workflows.
  - Say in the runbook that write access to the repo equals admin on the server.

### Should fix

- **[docker-compose.yml:20-21, 63-66]** The app, jobs and migrations all use the PostgreSQL superuser. This breaks FR-AUDIT-03, and §12 calls for a separate schema owner and app user. A superuser can also run `COPY … TO PROGRAM`, so any SQL injection becomes code execution in the DB container. The jobs log a warning about the purge account every day. **Fix:** an init script that creates an owner role (migrations), an app role (DML only, INSERT/SELECT on `audit_events`) and a purge role; pass `AUDIT_PURGE_DB_*` to `jobs`. Or record the gap in OQ-50 and decide later.
- **[docker-compose.yml:87-90]** Port 5009 binds `0.0.0.0`, and the deploy runs before the firewall rule exists. Until then any host that can reach <server IP> can use plain HTTP without the proxy's TLS or rate limits. **Fix:** make the bind address a variable that defaults to `127.0.0.1`, and set it to `<server IP>` once the firewall rule is in place and tested.
- **[docker-compose.yml:87-90, OQ-50]** Traffic from nginx to the app crosses the network in plain HTTP, carrying passwords, tokens and file content. This follows from the owner's choice of a remote proxy, but it isn't recorded. **Fix:** TLS on that hop, or record it in OQ-50 as an accepted risk, naming the network segment it relies on.
- **[docs/deploy/windows-docker.md, "Publishing a client release"]** The host `server\.env` holds the production `TOKEN_SECRET` and the DB superuser password in plain text. The CLI never issues tokens (it doesn't import `services/auth`); `TOKEN_SECRET` is only required to be 32+ characters. **Fix:** tell the operator to use a separate random `TOKEN_SECRET` there, and restrict the file with `icacls`.
- **[docs/deploy/windows-docker.md, "Trusting the proxy"]** The step can lead the operator to trust Docker Desktop's gateway address before the firewall rule exists, which would trust forged `X-Forwarded-For` from anyone who reaches 5009. **Fix:** say to set it only after the firewall rule is in place and tested.
- **[docker-compose.yml:32-36]** Storage on a Windows bind mount is untested. Inside the container `os.name == "posix"`, so `_fsync_directory` fsyncs directories on the mount (`storage/local.py:156-165`). If that fails on Docker Desktop for Windows, every chunk write fails while `/health/ready` still passes. **Fix:** add Windows checks that upload a multi-GB file end to end, and consider a Defender exclusion for `E:\DropShareData`.
- **[docs/requirements.md OQ-50]** "moving back is a settings change" is wrong once production holds data, because moving back needs a data migration too. **Fix:** reword.

### Nits

- **[docker-compose.yml:101,115]** `JOBS_INTERVAL_SECONDS` is never passed, so it is always 86400. Every deploy also restarts the schedule, so "daily" really means "at each deploy and then daily". Drop the mention or reword it.
- **[docker-compose.yml:12,120]** `dropshare/api` and `dropshare/watchdog` look like Docker Hub names; a `docker compose pull` would fetch someone else's images. Use a local-only name such as `dropshare-local/api`.
- **[.github/workflows/deploy.yml:42,69, Dockerfiles]** Actions and base images are pinned to tags, not commit SHAs or digests. `up --build` without `--pull` also never picks up security patches to base images.
- **[docker-compose.yml:11-41]** The api and jobs containers could add `cap_drop: [ALL]` and `read_only: true`. They already run as uid 10001 with `no-new-privileges`.
- **[deploy/watchdog]** The watchdog mounts `docker.sock` as root. Risk is already reduced (no network, read-only, the script has no injection path); document it as accepted.
- **[.github/workflows/deploy.yml:87-88]** On failure the workflow prints 100 log lines into Actions logs. Fine for a private repo.
- **[docs/deploy/windows-docker.md:26, host `.env` example]** Hard-coded `dropshare`/`5432` go stale if the variables change. Say "same values as the GitHub variables".
- **[docs/deploy/windows-docker.md:85]** The variables table needs a blank line before `### 5. Firewall`.
- **[docs/requirements.md §12]** The row label still says "Production (Linux)".

## Lessons for CLAUDE.md

- When a database setting bounds transaction time (an idle-in-transaction timeout or statement timeout), check every code path that holds a transaction across storage I/O. Upload `complete` assembles files of up to 10 GiB inside its transaction.
