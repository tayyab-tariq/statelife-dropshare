## Findings

### Blockers

- **[server/src/dropshare_server/services/file_policy.py:106, called from uploads.py `start`, nodes.py `move_node`, trash.py `restore`] The refusal audit takes a second database connection while the request still holds its first.**
  - `record_now` opens its own pooled connection while the request session is still open and still holds row locks. The pool is 5+10 connections, with about 40 worker threads.
  - Scenario: one signed-in user sends about 15 parallel `POST /uploads` naming `a.exe`. Each request holds a connection and waits for a second, so every request on the server stalls until the pool timeout (30 s). The audit writes then fail with a 500 and the `file.type_blocked` rows are lost.
  - Upload completion is not affected, because `_cancel` commits first.
  - Fix: roll back the request session before `record_now`, the same pattern as `_cancel`. Or carry the audit payload on the `AppError` and record it in the error handler, after `get_db` has released the session.
- **[server/src/dropshare_server/services/file_policy.py:57-71; trash.py:198] Refusing to restore a whole folder makes its allowed files unrecoverable.**
  - The folder rule was agreed in chat. What wasn't known then is that items inside a trashed folder can't be restored or deleted on their own: `_visible` returns 404 unless `trash_root_id == id` (trash.py:87).
  - Scenario: `Project/` holds 500 documents and one `setup.js` stored before `.js` was banned. The folder goes to the trash. Restore is refused, and nothing inside can be restored or deleted individually. "Rename or delete that file first" can't be done in the trash, and every file is purged when the 30-day retention ends.
  - This breaks the never-lose-data rule and FR-TRASH-02.
  - Fix (needs your decision): restore the folder and leave the banned files in the trash as their own trash items (give each its own `trash_root_id`). The alternative is to allow restoring folders. Then update OQ-57 (9).
- **[server/src/dropshare_server/services/sharing.py:211-219 and :243-272] Sharing gets around the check on moves into shared folders.**
  - `POST /nodes/{id}/members` on a folder moves its whole subtree into a new shared namespace with no `check_folder`. On a file stored before the ban, it creates a file share without a name check.
  - Scenario: the owner can't move `old.exe` into a shared folder, but shares its folder instead, and recipients sync `old.exe`.
  - OQ-57 doesn't cover sharing, so this needs a decision. Recommended: refuse with the same 422 (`check_folder` in `_share_folder`, `check_name` for file shares). That is consistent with (8).

### Should fix

1. **[client behaviour, triggered by services/nodes.py:226-229 and uploads.py:292-295] The installed 0.2.2 client repeats refused requests.**
   - A refused rename or folder move is held by `_hold_move_together` with backoff, capped at 60 s, so it is resent about once a minute indefinitely: roughly 1,440 refusals and audit rows per item per device per day.
   - A refused upload is planned again on every full scan, which clears Can't sync (`client/.../sync/core.py:609`, every 30 minutes and on start or wake). For executable content, the whole file (up to 3 GB) is sent again each time.
   - No data is lost: the server item is never trashed and the local file is never touched.
   - Fix: in the server, also run `executable_kind` when chunk 0 arrives (it needs only 64 bytes plus 4 bytes at `e_lfanew`) and refuse there. In 15c, hold refused items until the local file changes.
   - Either keep this server change off `main` until 15c ships, or raise `min_client_version` with 15c.
2. **[server/src/dropshare_server/services/uploads.py:277-280] The banned-name branch in `complete` relies on `check_name` raising.**
   - It cancels and commits, then calls `check_name`, which raises only because the same condition was tested just before.
   - If either condition changes, execution falls through into `storage.commit` and `_record_version` on an upload that is already cancelled.
   - Fix: return an `AppError` from a `refuse_extension()` method and `raise` it explicitly, as the executable path does.
3. **[.claude/skills/api-endpoint/references/conventions.md:41, :112] The conventions don't mention 422 `FILE_TYPE_NOT_ALLOWED` or `FileTypeNotAllowedDetails`.** Line 112 still says 422 is only FastAPI validation, which is turned into 400. Add the row and the typed details.
4. **[server/src/dropshare_server/services/uploads.py:407-419] An `OSError` in `_cancel`'s cleanup turns the 422 into a 500 with no audit row.** Nothing is lost, because the cleanup jobs sweep later. Fix: clean up on a best-effort basis (log the error), then audit and raise.
5. **[server/src/dropshare_server/services/nodes.py:224-229] The ban check runs before the existing refusals.**
   - Those are "into itself", name conflict, and the 403 for moving out of someone else's shared folder.
   - So an editor moving a pre-ban `.exe` out of someone else's shared folder gets 422 and a `file.type_blocked` row instead of 403.
   - The comment "Only node rows are locked" also misses the namespace-root locks.
   - Fix: move the check after the name-conflict check and correct the comment.
