## Findings

### Blockers

- **[server/src/dropshare_server/services/blobs.py:117-119] gc-blobs can delete the blob of a version that has just become visible.**
  - `_unknown` asks `known_blob_keys` (file versions) first and `scanning_blob_keys` second. Under READ COMMITTED, each is its own snapshot.
  - Scenario: an upload waits longer than 24 h (ClamAV down), so its blob is past the grace period. The worker commits `record_version` between the two queries. The first query didn't see the version yet; the second no longer sees the upload as scanning. The blob is deleted, and the live file points at nothing.
  - Fix: query `scanning_blob_keys` before `known_blob_keys`, with a comment on why the order matters, and add a test.
- **[server/src/dropshare_server/services/uploads.py:300-307] A retried `complete` that waited behind a deferral gets 404.**
  - Scenario: a large file's assembly outlasts the 90 s proxy timeout, and the client retries. The retry blocks on the row lock while the first `complete` defers. After the lock, the status is `SCANNING`, which `_require_pending` rejects as "expired or cancelled".
  - 0.2.2 treats 404 as final: it calls `DELETE`, cancelling the waiting upload, then uploads the whole file again and hits the same timeout, in a loop.
  - Fix: answer 202 when the locked row is `SCANNING`, and add a concurrent-complete test.
- **[.github/workflows/deploy.yml:90,93,102] The first deploy with ClamAV fails.**
  - `docker compose up --wait --wait-timeout 240` now waits for `clamav` to be healthy, and its first signature download and load can take longer. The readiness check then needs `scanner: ok`.
  - The logs step on failure shows only `api jobs`.
  - Fix: leave `clamav` out of `--wait`, or raise the timeout. Retry readiness with a longer budget, and add `clamav scanner` to the logs step.

### Should fix

1. **[repositories/uploads.py:52-58] `lock_next_to_scan` locks every candidate (up to 20) for the whole scan.**
   - A 2 GB scan holds them for minutes. Meanwhile emptying the trash for their folders answers 409, and cancelling any of them blocks.
   - Fix: lock candidates one at a time, with `skip_locked`.
2. **[services/uploads.py:676-684, also the PENDING branch at :301] `cancel` (and `complete`) wait on the worker's row lock with no limit.**
   - Each waiting request pins a thread and a DB connection for up to 15 minutes, so repeated `DELETE`s exhaust the pool.
   - With 0.2.2, saving the same large file twice during a scan can end in a conflict copy of the user's own edit.
   - Fix: when the row is held, answer immediately (409, or 202 "may still complete"), and define this for 15c.
3. **[services/uploads.py:341, services/health.py:53] The inline scan and `/health/ready` use the worker's 900 s reply timeout.**
   - If `clamd` stalls, a `complete` for a file of 64 MiB or less holds the upload row and a connection for up to 15 minutes, well beyond the client's 60 s.
   - `/health/ready` is public through the proxy, so anonymous requests can pin connections the same way.
   - Fix: a short overall timeout for inline scans (about 30 s; defer when it runs out) and for the readiness `VERSION` call. Optionally cache the scanner status for a few seconds.
4. **[services/scans.py:66-68, 86-89, 108-112] The worker isn't robust to one bad file.**
   - Any per-file error counts as "scanner down": a `clamd` error on that content, or a missing blob (`OSError`). That ends the batch and is retried forever, so one file can stall the queue or keep crashing `clamd`.
   - Exceptions other than `AppError` (`RuntimeError`, `IntegrityError`, database errors) end `--loop`, and the restarted worker picks the same row first.
   - Fix: wait globally only when `version()` fails. Otherwise back off just that upload and carry on. Reject as unscannable (audited) after N tries. Catch, log and postpone unexpected errors per upload.
5. **[services/uploads.py:431-447] `_rejection` replays worker refusals with the wrong status or missing details.**
   - `FORBIDDEN` (lost edit rights while waiting) comes back as 409 "send it again". `NAME_CONFLICT` comes back without `NameConflictDetails`.
   - Fix: store and replay the original status, rebuild the name-conflict details, or answer every non-malware rejection with a code 0.2.2 abandons on.
6. **[services/scans.py:130-136, 166-183] The worker publishes waiting uploads without re-checking the uploader, and doesn't audit its own refusals.**
   - A user disabled, or a device revoked, while their upload waited still gets it published.
   - Refusals for lost access, quota or conflicts write no audit row, and worker events have no `request_id` to link them to the `complete` call.
   - Fix: check that the user is enabled and the device isn't revoked before `record_version`. Audit refusals. Store the request ID on the upload.
7. **[services/scans.py:176] Layering: a locking ORM query in a service** (`session.get(UploadSession, …, with_for_update=True)`). Use `upload_repository.get_for_update`.
8. **[docs/requirements.md §9 and §15; .claude/skills/api-endpoint/references/conventions.md:42-60, 114; references/storage.md:36] The docs don't describe 202 or `MALWARE_DETECTED`, nor how 0.2.2 behaves.**
   - The conventions file still says `complete` answers 200 and that "Our only 422 is `FILE_TYPE_NOT_ALLOWED`".
   - Not recorded for 0.2.2 clients:
     - large or deferred shared-file versions show a false "doesn't understand" error and can upload the same content again as an extra version;
     - files are held back while uploads wait (their quota reservation).
   - Fix: update §9 and the conventions file. Record a §15 interim for 0.2.2, and decide whether `MIN_CLIENT_VERSION` goes up with 15c.
9. **[deploy/clamav/clamd.conf:17-24] The comment says the archive limits are at clamd's maximums, but they're defaults** (`MaxFiles` 10,000, `MaxRecursion` 17, …). With `AlertExceedsMax`, an ordinary archive of more than 10,000 entries is refused and audited as malware. Fix: set them explicitly, or correct the comment and OQ-58 (2).
10. **[docker-compose.yml] `clamd` parses untrusted files but sits on the database's network, with outbound internet and default capabilities.** It also accepts `SHUTDOWN`/`RELOAD` from any container there. Fix: give it a network shared only with `api` and `scanner`, add `cap_drop` with the minimum it needs, and set `MaxQueue`/`MaxThreads` so worker and inline scans don't starve each other.
11. **[.claude/settings.json:35,37] Your local change shouldn't be committed.** Commenting out the two `.env.*` deny rules makes the file invalid as strict JSON, which risks the whole file being rejected along with its hooks and other denies. It also opens git-ignored `.env.local`/`.env.production` files to agents. Keep it out of the commit; if needed, narrow the rules.

## Fixes applied (after approval)

The user approved fixing everything, with the recommended answers for the two open choices: cancelling an upload being scanned answers 409 at once, and `MIN_CLIENT_VERSION` is decided in 15c (interim recorded as OQ-58 (5)).

- **Blocker 1, gc race:** `_unknown` asks for scanning uploads before file versions, with a comment explaining why. The test publishes the upload between the two lookups. It fails with the old order (1 blob collected) and passes with the new one.
- **Blocker 2, 404 on retry:** `complete` locks with `skip_locked` and answers 202 with the upload's state whenever the row is held or `SCANNING`. The answer carries `Retry-After: 5`. Two tests cover it.
- **Blocker 3, first deploy:**
  - `clamav` is started first, without waiting on it; the other services are waited for as before;
  - readiness is polled for up to 20 minutes;
  - the logs on failure include `scanner` and `clamav`;
  - after readiness, `clamdscan --reload` loads freshly downloaded signatures. This was found while re-testing: on a first start, `clamd` kept the image's bundled signatures.
- **Should-fix 1, worker locking:** `lock_next_to_scan` locks exactly one row (candidates one at a time, `skip_locked`). Test: the other upload stays free.
- **Should-fix 2, cancel waiting:** `cancel` answers 409 `UPLOAD_SCANNING` at once when the worker holds the row. New `ErrorCode`. Test.
- **Should-fix 3, timeouts:**
  - `ClamdScanner` enforces a total deadline, not one per socket call;
  - the API's scanner uses `SCAN_INLINE_TIMEOUT_SECONDS` (30 s) and defers when it runs out;
  - `/health/ready` uses a separate scanner limited to the connect timeout (5 s).
- **Should-fix 4, worker robustness:**
  - if the scanner doesn't answer at all, everything waits untouched, and the loop's pause doubles up to the maximum;
  - a file the scanner fails on is retried on its own, with backoff, and refused as `DropShare.Unscannable` after `SCAN_MAX_ATTEMPTS` (5);
  - unexpected errors are logged and the file postponed while the batch carries on;
  - a missing blob ends the upload with 404 (the client sends the file again).
  - Tests for each.
- **Should-fix 5, replayed refusals:** `FORBIDDEN` is replayed as 403 (`view_only`), and `NAME_CONFLICT` with its details. The current revision is shown only to someone who can still see the file. Anything else becomes 404 "start again". Tests.
