## Findings

### Blockers

1. **[client/src/dropshare_client/sync/reconciler.py:250-252, core.py:604-633] The "held" rename isn't stored, so a partial cycle trashes the server copy.**
   - A move to a refused name is parked only when one cycle collects both the old name and the held new one. Partial cycles, driven by watcher hints or another device's changes, don't. `_local_location` then finds nothing, and the old name is read as deleted here.
   - Scenario: `Reports/` is renamed locally to a refused name, then another device adds `Reports/new.docx`. The cycle for `reports` plans DELETE_REMOTE for `Reports/a.docx` and the rest. They go to the server trash and every other device's Recycle Bin, under the mass-delete threshold, so nobody is asked.
   - Also reachable through a parent-folder rename.
   - The new tests use full scans only, which is why they pass.
   - Fix:
     - store parked moves in the index (old key, node ID, target key, target file ID);
     - in `_collect`, whenever a root covers a parked old key, collect its target too, or defer the old subtree while the held item exists;
     - clear the record when the item is renamed back, disappears, or the node is gone;
     - add partial-cycle tests (`local=`).
2. **[client/src/dropshare_client/sync/scanner.py:228] Files synced before their type was banned become permanent "Can't sync" items.**
   - The scanner refuses every banned name, including unchanged synced files, which OQ-57 (2) says stay and can be downloaded. Once on disk:
     - they're listed for good, and after the update every device notifies "N items can't be synced" (`.js` is banned, so a web project floods the list);
     - remote deletes and renames of them never reach this device;
     - deleting on the server a folder that holds one brings the folder back there (`_folder_deletes` sees a deferred child).
     - View-only marking skips them, and `_expect_folder_unchanged` raises for folders holding one.
   - Fix: refuse a banned file only when it's new or changed against its base entry. An unchanged synced file stays synced and download-only. Test it with a remote file stored before the ban.

### Should fix

1. **[core.py:231-234] A failed ban-list fetch on connect isn't retried.** The list is fetched after `_namespace` is set, so `connected` is already true. If `GET /file-policy` fails, the list stays empty all session and every banned file is sent once to be refused. Fix: fetch it before marking connected, or keep the previous list and fetch again later.
2. **[services/files.py:379-381, 433-437] A 409 `UPLOAD_SCANNING` on cancel is swallowed.**
   - Saving a file again while its previous upload is being scanned starts a second upload on the same base revision. The first publishes, the second gets `REVISION_CONFLICT`, and the user gets a conflict copy of their own edit.
   - The log line "expires on its own" is also wrong in this case: the upload will be published.
   - Fix: on `UPLOAD_SCANNING`, keep the session and raise `ScanPendingError`.
3. **[controllers/shared_controller.py:174] A shared-file version that gets a 202 is never checked again (FR-SAFE-01 "the user is notified").** If the scan refuses it, nobody is told, and the message said "there's no need to upload it again". Fix: poll `complete` in the background until the final answer and report it. At least, word the message so it doesn't promise success.
4. **[core.py:934-939] No backoff while waiting for the scan.**
   - A retry every 5 s for as long as ClamAV is down (OQ-55). Each one rehashes the whole file, up to 2,000 MiB, and makes two requests.
   - Fix: `max(retry_after, backoff(key))`, capped (about 5 minutes) and reset once settled. Avoid rehashing while an upload session for the same size, mtime and file ID exists.
5. **[core.py:934; reconciler `_decide`] A new file deleted or renamed while it waits for its scan isn't followed.**
   - No base exists until the scan ends. After it's published, a local delete makes the reconciler download the file again. A rename uploads it again under the new name, so the server holds both.
   - No data is lost, but the user's delete is undone, or a duplicate appears.
   - Fix: keep a "scanning" record per upload. On a local delete, cancel (or trash once published). On a rename, adopt the published node and send the rename as a move.
6. **[controllers/notification_controller.py:171-172] The set of virus paths only grows.** A later, unrelated problem at a path once refused as a virus is announced as "A virus was found…". Fix: rebuild the set from the current problems on each report.
7. **[controllers/upload_controller.py:204-205] The list of files left out of an upload appears only in the status line, which clears after 6 s.** It's lost before it can be read, or before Narrator finishes. "Nothing was added" is sent as a success. Fix: send it as a lasting message (the error line) when files were left out, and treat "nothing added" as a failure.
8. **[core.py:1037-1055, 635-648] A refused folder move can't be resolved as the server's message suggests.**
   - The refusal is keyed on the folder's own size and mtime and defers the whole subtree. Deleting the banned file inside doesn't sync, and the move is refused again.
   - A refusal also outlives the server's copy of the folder.
   - Fix: tie a move refusal to the base node, and drop it when the node or base is gone. Branch on `reason == contains_banned_file`. Let deletes inside run before the move is retried.
9. **[core.py:709] Held files are never hashed, so move detection can only match them by file ID.**
   - A tool that saves a new copy under a refused name and deletes the old one (a different file ID, same content) gets DELETE_REMOTE on the old name.
   - Before M15c that case became a refused move, not a trash.
   - Fix: hash held files that are candidates when a base file of the same size is missing.
10. **[controllers/files.py `_UPLOAD_OVER`] A 403 `FORBIDDEN` replay from a rejected upload is never abandoned.** The rejected session lingers: if access returns and the same content comes back, it is refused again. Fix: abandon on any error once the resumed upload's status is `rejected`.
11. **Wording:**
    - **[sync/scanner.py:39-42]** "Rename it to another type" points at a way round the policy, and the server's content check makes it useless for programs. Drop it; keep "Keep it outside your DropShare folder".
    - **[sync/status.py:50-53]** The "couldn't check" reason gives no next step (FR-SYNC-07, NFR-UX-03).

## Fixes applied (after approval)

- **Blocker 1, held renames in partial cycles:**
  - a new index table, `held_moves`, records every held move: client-held ones (refused names) and server-refused ones;
  - a cycle that looks at either end also collects the other end;
  - if a held item has moved on and the cycle doesn't see everything, nothing is planned and a full scan runs first;
  - the server-side key of a held move is held too, so another device's rename doesn't move the user's held file.
  - Tests use partial cycles (`local=`): a held folder when another device adds to it, a held file edited elsewhere, a parent-folder rename, a rename to an allowed name, and a server rename. Three of these fail with both safeguards switched off; either safeguard alone passes them.
- **Blocker 2, files synced before their type was banned:**
  - `LocalScan.accept_synced` keeps an unchanged synced file of a banned type synced, both in the cycle and in the executor's check before recycling a folder;
  - read-only marking now covers held files.
  - Tests: remote edits and deletes still arrive; an edit made here isn't sent.
- **Should-fix 1, ban-list fetch:** fetched before the engine counts as connected, so a failure means connecting is retried. Test.
- **Should-fixes 2 and 5, changes during a scan:**
  - a cancel answered with 409 `UPLOAD_SCANNING` keeps the session and waits;
  - the engine adopts its own uploads once published (`_adopt_own_uploads`), so a delete, rename or edit made during the scan syncs as such.
  - Tests: a delete during the scan, a rename during the scan, and an edit while the earlier version is scanned (no conflicted copy).
  - A new file renamed during its scan is uploaded once more under its new name, and the published original then goes to the trash. Recorded as OQ-59 (5).
- **Should-fix 3, shared-file versions:** the controller asks again in the background (same base revision, so nothing is sent again), waiting longer each time up to 5 minutes, and reports "published" or the refusal. The message no longer promises success. Two tests.
- **Should-fix 4, waiting for the scan:**
  - the waits double up to 5 minutes;
  - a cache of the file's hash stops it being rehashed while it waits;
  - stopping sync during a wait no longer logs a traceback.
  - Test.
- **Should-fix 6, virus notice:** the set of virus paths is rebuilt from the current list on every report. Test.
- **Should-fix 7, upload summary:** when files were left out, the summary goes to the error line, which stays on screen. Test updated.
- **Should-fix 8, refused moves:** a rename or move the server refuses (a type banned since, or a folder holding a banned file) is a held move. The server keeps the item where it was, the message says to rename it back, and the hold is dropped when the node is gone or the item has moved on.
- **Should-fix 9, held files:** they're hashed when a synced file of the same size is missing, so a move can be matched by content.
- **Should-fix 10, rejected uploads:** a rejected upload is let go whatever the replayed answer. Test with a 403 replay.
- **Should-fix 11, wording:**
  - the banned-type message no longer suggests renaming the file to another type;
  - the "couldn't check" message gives a next step.
- **Nits fixed:**
  - "your administrator" throughout;
  - no "(unknown)" when no detection name is sent;
  - the plural virus notice has the reassurance too;
  - "its type" or "their types", and "added" rather than "copied";

  - `Retry-After: nan` is rejected;

## Re-review of the fixes (sync-reviewer)

No blockers. Three should-fixes and two nits, all fixed:

- **A held file saved by a "safe save" editor** (new file ID and size) was no longer matched, so its old name read as deleted.
  - Fix: while a held move's target is still refused, its old key and the node's current server path are deferred whether or not the item is matched. - **Adoption could take someone else's identical file** for a session left behind.
  - Fix: `_published_as` asks the server (`GET /uploads/{id}`) and adopts only an upload that completed as this very node. The entry and the session change in one index transaction (`adopt_upload`). Keys in flight are skipped.
  - Test: a left-behind session and another device's identical file. It fails without the check.
- **The server-side end of a held move** wasn't part of the hold, so a held file renamed and then edited elsewhere was downloaded beside it.
  - Fix: `_partners` and `_hold_moves` include the node's current server path. Test.
- **Nits fixed:** the cached hash is dropped once the file is done or adopted, and the scan-wait backoff is reset on adoption.
- **Still open (nits):**
