### Should fix

All four fixed after the audit; see **Fixes applied** below.

- **[client/src/dropshare_client/ui/forms.py:33-39, ui/trash_view.py:134, controllers/trash_controller.py:206-217]** A reload failure overwrites an action error that is still showing; when a later reload works, the label hides and the action error is gone.
  - *Scenario:* restoring 5 items, the network drops after 3. "2 couldn't be restored…" shows, the automatic `refresh()` fails offline and replaces it with "Can't reach…", then Refresh works and the label hides. The user never learns 2 items stayed in the trash.
  - *Same on My files:* the reload after a `stale` action, or a refresh after an upload or rename error.
  - *Before this session* the action text was already replaced, but a message stayed visible.
  - *Suggested fix:* `show_message(..., from_reload=True)` must not replace a visible unmarked message. Keep the action text, or show both ("action text, then reload text") and let `clear_reload_message` restore the action text instead of hiding.
- **[client/src/dropshare_client/ui/settings_view.py:235-237, 252-261]** Same problem in Settings, and the lost message is never shown again. "Installing the update failed; it's still ready" is replaced by a failed computer listing, then cleared when the listing works. `updates.error != self._update_error` stops it from coming back. *Suggested fix:* keep the transient message and the reload message in separate fields and join lasting + transient + reload in `_show_error`.
- **[client/tests/test_settings_ui.py:630]** After the failed listing, the test waits only for `!= "Lasting."`. It would also pass if the label went blank, so it doesn't prove the reload message shows next to the lasting one. *Suggested fix:* assert the exact `"Lasting.\n\n" + message`.
- **[client/tests/test_settings_ui.py]** Settings has its own `_reload_error` flag, but no test checks that an action error survives the reload after it. For example: a revoke fails, `devices.refresh()` then succeeds, and the message must stay. *Suggested fix:* add that test. Optionally add the same for an Activity `action_failed` (e.g. `NO_SYNC_FOLDER_YET`) followed by `client.activity.refresh()`.

### Nits

- **[client/src/dropshare_client/controllers/sync_log_controller.py:159-162]** `ActivityController._added` emits `loaded` for each event the engine pushes, so "Couldn't read the activity" clears without a successful index read. The signal comment says "the next reload that works clears it". I flagged this in the hand-off. Either give `_added` its own signal or document that a pushed event counts. `CantSyncController._changed` is fine, because it sends the engine's full list.
- **[client/src/dropshare_client/ui/browser_view.py:234]** A successful Load more (`appended`) clears a refresh-failure message while the rows above are still from before the failed refresh. The server is reachable again, so this is acceptable. Add a one-line comment.
- ~~**[client/src/dropshare_client/ui/settings_view.py:259-261]**~~ *Fixed with Should fix 2.* When the reload part is removed, `show_message` raises the Alert again for the lasting text, so screen-reader users hear the folder-move warning again unprompted. *Suggested fix:* update the text without an Alert when only the reload part goes.
- **[client/src/dropshare_client/ui/forms.py:39-41]** A background reload that keeps failing re-announces the same text each time (Activity and Can't sync reload on every engine report). This happened before the session. Skip the Alert when `from_reload` is set and the visible text hasn't changed.
- **[client/tests/test_sync_log_ui.py]** The test corrupts and restores `index.db` with `write_bytes`. It passed 20/20 on the Mac, and the fixture runs no engine. It could behave differently on Windows if anything holds the file open. Confirm on the Windows machine.

## Fixes applied (after approval)

- `ui/forms.py`: `show_message(..., from_reload=True)` keeps a message already shown (unmarked) in front of the reload's text. A repeat reload failure keeps the same kept part, and identical text isn't shown twice. `clear_reload_message` goes back to the kept part without a new Alert. New `alert` keyword on `show_message`.
- `ui/settings_view.py`: the single flag is replaced by separate parts (lasting, latest message, reload failure) joined in `_show_messages`. A working listing removes only the reload part, without re-announcing. This also resolves Nit 3 (lasting message re-announced).
- Tests:

  - My files: a taken-name error kept through a failed and then a working reload.
  - Settings: a revoke that fails offline is kept through a failed and then a working listing.
  - Settings: the lasting + reload assertion is tightened.
